# Napell Farmer Connect

Aeroponic coffee supply-chain identity, traceability and compliance network.

Modelled on the three-product shape of farmerconnect.com — farmer identity, a supply-chain
data hub, and a consumer scan experience — but built on a closed-system foundation where the
evidence is generated by the chamber controller rather than self-reported by the seller.

**Live site:** <https://www.napellconnect.space/> — the full front end, driven by a captured
read-only snapshot of the same API (see *Static build* below).

```
farmerconnect          →  this system
──────────────────────────────────────────────────────────────────────────
FarmerID               →  GrowerID / ModuleID   credentials from sensor + ledger volume
ConnectHub (IBM Food Trust) → Napell Hub        hash-chained event ledger + REST API
ThankMyFarmer          →  Thank My Farm         scan-to-journey with computed impact
(no equivalent)        →  Compliance engine      EUDR dossier + LCA issued at harvest
```

---

## Why the argument is different

EUDR asks one hard question: was this coffee produced on land deforested after 31 December
2020? For an open-field plot that means polygon mapping, satellite time series and a
defensible inference. Aeroponic production has no plot, so the question is met by
construction rather than by inference.

The trade-off is disclosed rather than hidden: closed-environment cultivation is
electricity-intensive. At the network's recorded renewable share the carbon figure beats the
conventional baseline; at 0% renewable it does not, and the platform reports both.

| Metric (per kg green coffee) | Aeroponic | Conventional baseline | Delta |
|---|---:|---:|---:|
| Blue water withdrawal | 1.98 L | 250 L | −99.2% |
| Land occupied (floor) | 0.385 m² | 10 m² | −96.2% |
| Energy intensity | 6.5 kWh | 1.8 kWh | **+261%** |
| Carbon footprint | 2.01 kg CO₂e | 2.40 kg CO₂e | −16.3% |
| Deforestation exposure | 0.00 | 0.32 | −100% |
| Agrochemical load | 0 | 0.012 kg | −100% |

Aeroponic figures are computed from the batch's own ledgered inputs. Conventional figures are
pooled literature medians and are labelled as reference in every API response.

## Run it

```bash
# 1. dependencies (isolated venv)
"C:/Users/wangx/.workbuddy/binaries/python/versions/3.14.3/python.exe" -m venv .venv
.venv/Scripts/python -m pip install -r backend/requirements.txt

# 2. start (seeds itself on first boot)
cd backend
../.venv/Scripts/python -m uvicorn app.main:app --reload --port 8780
```

Open <http://127.0.0.1:8780/>.

Seed data is deterministic: 3 growers, 4 facilities, 12 chambers, 8 batches, 2,016 telemetry
rows, 191 ledger events, 8 filed compliance dossiers.

```bash
# rebuild the demo network from scratch
python -m app.seed --force

# end-to-end smoke test (35 assertions, including live tamper detection)
python tests/smoke.py
```

## Layout

```
index.html …       static multi-page front end — the repository root IS the site,
assets/            so GitHub Pages can publish it with a main/root build
  assets/data/     read-only snapshot + QR files used when no backend is present
backend/
  app/
    config.py      lifecycle stages, LCA baselines, EUDR constants
    db.py          SQLite schema and helpers
    ledger.py      sha256 hash chain: append, tail, verify
    domain.py      LCA engine, EUDR dossier builder, scoring, telemetry simulation
    services.py    journeys, roll-ups, grower scoring, analytics
    seed.py        deterministic demo network
    main.py        FastAPI application, 40 endpoints
  tests/smoke.py   35-assertion end-to-end test
  tools/export_snapshot.py   captures the read API for the static build
  data/            SQLite database (gitignored)
docs/SPEC.md       data model, ledger format, API contract, compliance mapping
CNAME              www.napellconnect.space
_config.yml        Pages build: excludes backend/, docs/ and notes from the site
```

Serving the site from the same folder as the backend means the dev server would also expose
`backend/`, `docs/` and the SQLite file. `SiteFiles` in `app/main.py` denies those prefixes, so
even a `--host 0.0.0.0` demo only ever publishes the site itself. (Watch the Windows trap
documented there: Starlette normalises the request path to backslashes before the check.)

## Static build (GitHub Pages)

Pages serves files, not processes, so the published site has no FastAPI behind it. Every read
falls back to `assets/data/snapshot.json`, captured from the running API:

```bash
cd backend
python tools/export_snapshot.py                 # defaults to http://127.0.0.1:8780
python tools/export_snapshot.py --base http://host:port
```

Re-run this after any change to the seed data or the API, and commit the result. The fallback:

* returns the **same payloads** the live API returned — it is a capture, not a mock;
* reproduces filtered collections exactly (the client filters the captured superset, sorts by
  `seq` descending and applies the limit, the same order the server uses);
* rebuilds the LCA renewable-share slider from its 0 % and 100 % endpoints. The model is
  strictly linear in that share, so this is arithmetic rather than approximation — the
  endpoints are byte-identical to the API and an intermediate position can differ by at most
  **0.001 kg CO₂e/kg** (0.1 pp on the delta), purely because the API rounds each captured
  endpoint to three decimals;
* fails writes with a clear message, and the nav LED turns amber and reads
  `snapshot · N events · chain ok` so a read-only build is never mistaken for a live one.

QR codes are exported as real SVG files, so the consumer scan page works offline too.

## Ledger

```
hash_n = sha256(seq | ts | entity_type | entity_id | event_type | actor | payload | hash_{n-1})
```

`GET /api/v1/ledger/verify` recomputes the whole chain from genesis. Change one historical
payload and it reports the exact sequence where the break occurs. The smoke test performs that
edit against the live database and asserts detection.

Hash chaining proves the record was not altered after the fact. It does **not** prove the
sensor was honest — that needs hardware attestation, which is listed as an open gap rather
than papered over.

## Status

Demo build. Offline by default (`NAPELL_OFFLINE=1`), no external calls, synthetic data.
API is unauthenticated for review convenience; attribution through `X-Napell-User` is still
enforced and hashed into every write.

The published site is a read-only capture — write actions (issue dossier, ingest telemetry,
register grower, tip) are disabled there and say so when clicked.
